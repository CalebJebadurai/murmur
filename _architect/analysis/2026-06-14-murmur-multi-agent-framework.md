## 1. Executive Summary

The user has built an unusually mature multi-agent system inside VS Code Copilot — seventy-one agent definitions across three projects, orchestrated by hub agents such as `architect` and `real-estate-master` that selectively dispatch a roster of specialists through the `agent/runSubagent` tool. The system works, but it suffers from a structural flaw that limits its reuse: project-specific knowledge is baked directly into agent bodies rather than externalized into skills and instructions. The analyst found that the thirty-two `re-*` real-estate agents are roughly one hundred percent domain-bound, that agri agents hard-code AgriRide and farmer facts, and that forty to seventy percent of critic and orchestrator bodies are project-specific and duplicated-with-drift across the personal, agri, and elec projects. The consequence is that none of this work is portable: every new project requires hand-copying and re-editing agents, and the same conceptual agent (a critic, an implementer) exists in three slightly different forms.

Murmuration solves this by inverting the architecture. Agents become generic and codebase-agnostic; all contextual knowledge moves into skills (domain knowledge) and instructions (scoped behavioral rules); a master agent spawns specialized subagents on demand when no existing specialist fits; an `init` workflow generates the skills and instructions for any codebase in two passes — a deterministic structural pass that reads `package.json`, `tsconfig.json`, the directory tree, lockfiles, test config, and CI files with no LLM at all, and an optional semantic pass driven by whatever host agent the user already runs; and a compiler emits the abstract definitions to multiple runtimes (Copilot, goose, Claude Code, Cursor, and ultimately the Agent Client Protocol). The whole thing ships as a `bun` CLI that can be dropped into any project. The recommended approach is a phased build that proves the abstraction with two structurally dissimilar compile targets first (Copilot and goose), defers the near-isomorphic and harder runtimes and global commands to later milestones, and treats the context-stripping `publish` step as a first-class defense-in-depth safety layer rather than an afterthought.

The honest differentiation must be stated in two tiers. The shipped v0.1.0 differentiator is the only local, open-source tool that combines deterministic structural auto-init, compile-once/emit-many across two structurally-different runtime paradigms (persona-Markdown and parameterized-recipe), knowledge externalization enforced by a CI gate, and a defense-in-depth publish scrubber — a concrete, buildable union. The aspirational v1.0 differentiator additionally folds in ACP protocol portability, first-class spawnable specialists proven across runtimes, and semantic codebase init, which together no competitor offers. Keeping these tiers separate is what preserves the document's credibility: the launch claim describes what the product actually does, and the roadmap claim describes where it is headed, without conflating the two.

## 2. Problem Statement & Context

The user's current state is a sophisticated but non-portable agent ecosystem. The analyst's inventory counted seventy-one agent files (forty-nine in the personal project, twelve in agri, ten in elec), only two instruction files, a single vendored skill, and zero prompt files. The agent format is consistent and well-understood: each lives at `.github/agents/<name>.agent.md` with YAML frontmatter carrying a `description` that opens with a `"Use when: …"` trigger phrase, plus optional `tools`, `agents`, `model`, `user-invocable`, and `disable-model-invocation` fields, followed by a prose instruction body. Agent identity is the filename. The `architect.agent.md` file is the closest existing analog to the master agent Murmuration envisions — it operates as a central hub with selective-dispatch tables, parallel-execution caps, loop limits, and a fifteen-agent roster invoked through `agent/runSubagent`, with subagents forming a multi-tier tree.

The problem is threefold. First, knowledge externalization is almost entirely absent: the skills directory that should hold domain context is effectively empty, while agent bodies are saturated with project facts. This is the central anti-pattern Murmuration exists to fix. Second, there is duplication-with-drift: a recurring core archetype of roughly ten agents (critic, implementer, researcher, planner, verifier, and so on) appears in all three projects in subtly divergent forms, so a fix or improvement in one does not propagate. Third, there is no packaging or portability story: the agents are Copilot-only, there is no `bin` entry anywhere in the workspace, and there is no mechanism to initialize a fresh project, compile to another runtime, or strip context before sharing. The user wants to convert this artisanal, copy-paste practice into an engineered, installable product. Four design decisions are already locked: the target is tool-agnostic with multi-runtime compilation; distribution is a CLI (`bunx murmur init`); the init analyzer runs inside the host agent runtime with no separate API key; and the design synthesizes best practices from Claude Code sub-agents, goose skills and recipes, the ACP decoupling standard, and ECC.tools/Hermes orchestration patterns.

## 3. Research Findings

The industry research produced one correction that materially reshapes the framing. The brief assumed dynamic subagent spawning was a clear differentiator because goose lacks it, but the researcher found that goose does support subagent delegation through its `summon` extension, and that ECC.tools ("Everything Claude Code") already sells a repo-history-to-skills capability across four harnesses. The honest conclusion is that no single capability is unique to Murmuration; the differentiator is the *union* of capabilities that no competitor offers together: local codebase auto-init, compile-once/emit-many output (including ACP), first-class spawnable specialists, goose-grade composable skills, and — most distinctively — a context-stripping publish step. This reframing is important because it changes the marketing claim from "we invented X" to "we are the only tool that combines X, Y, and Z," which is both more defensible and more honest.

The per-system lessons are concrete. From goose (now stewarded by the Agentic AI Foundation at the Linux Foundation), Murmuration should adopt the composable-knowledge model: skills authored once at the repository root and mirrored into `.claude`, `.codex`, and `.cursor` directories for discoverability, recipes with typed parameters and declared MCP extensions, and AGENTS.md-to-CLAUDE.md parity. From Claude Code, Murmuration should adopt the named-persona subagent model: Markdown with YAML frontmatter, per-agent model and tool selection, isolated context windows, description-driven auto-delegation, and a clear precedence order (managed, then project, then user, then plugin). From ACP, the lesson is that it is the only genuine *protocol* portability target — an LSP-for-agents using JSON-RPC over stdio that reuses MCP's JSON types — making it the highest-leverage long-term interoperability decision. AGENTS.md emerges as the de-facto universal manifest, adopted by tens of thousands of repositories and roughly a dozen tools, so Murmuration should treat it as the lowest-common-denominator fallback. ECC.tools and Hermes (the NousResearch self-improving-skills agent) are relevant conceptually but their internals are not public, so the comparison must be explicitly labeled as based on public materials only. The existing-patterns analysis confirms that the user's `.agent.md` schema, the `applyTo`-globbed instruction format, and the empty-but-intended skills directory map cleanly onto Murmuration's abstract schema, and that the recurring ten-agent archetype is the natural seed for a generic base library. Packaging should follow the agri project's bun-plus-turbo workspace conventions and TypeScript ^5.7, with `chat/build.py` serving as the existing precedent for a markdown-compile step.

## 4. Goals, Non-Goals & Constraints

The goals are precise. Murmuration must define an abstract schema for agents, subagents, skills, and instructions that is runtime-neutral. It must provide a bun CLI with the commands `init`, `add`, `compile`, `doctor`, `publish`, and the `list`/`update` helpers. It must include a codebase-analyzer that runs inside the host agent runtime to generate project-specific skills and instructions. It must compile to at least two runtimes initially — Copilot and one other — through a plugin architecture that makes adding runtimes a matter of implementing one interface. It must implement master-agent orchestration with dynamic subagent spawning. It must implement a publish step that scrubs repository names, file paths, domain terms, secrets, and PII. And it must be packaged for distribution with correct bin linking and a tarball under ten megabytes. Above all, generic agent bodies must contain zero codebase-specific facts; that property is the framework's reason to exist and is therefore a hard acceptance gate.

The non-goals keep the first version tractable. Murmuration is not an agent execution runtime — it produces definitions that existing runtimes execute. It ships no hosted services, no cloud infrastructure, no GUI or IDE extension, and no custom inter-agent messaging protocol beyond each runtime's native subagent invocation. It collects no telemetry. It does not auto-migrate the user's existing seventy-one agents, does not guarantee feature parity on runtimes that lack subagent or skill primitives, and does not perform legal review of scrubbed output. The constraints are equally firm. The CLI runs on bun version 1.0 or later. File operations must be safe: `init` must never overwrite without confirmation, and `publish` must write to a separate output directory rather than mutating the source. The analyzer must respect host-runtime token limits, chunking or sampling when a codebase is large. The package must stay small and must not create a hard dependency on any single proprietary runtime — if Copilot disappears, the abstract definitions remain valid and recompile elsewhere. Finally, GitHub remote creation is blocked on valid `gh` authentication; the repository exists locally with one commit but has not been pushed, and this must be resolved before any CI workflow can run.

## 5. Analysis of Approaches

Three fundamentally different architectures could satisfy the brief, and they differ chiefly in where the abstraction boundary sits.

The first approach is a **template-and-copy scaffolder**. In this model Murmuration is essentially a sophisticated `create-*` tool: it ships a library of pre-written generic agents, skills, and instructions as templates, and `init` copies the appropriate ones into the target project, lightly parameterized with the project name and a few detected facts. There is no abstract intermediate representation and no real compiler — each runtime gets its own template set. The advantage is speed of delivery and conceptual simplicity; the user could have a working tool in days, and the templates are easy to inspect and edit. The fatal weakness is that it does not actually deliver portability or knowledge externalization in any principled way. Maintaining parallel template sets per runtime reintroduces the very duplication-with-drift problem that motivates the project, and the codebase analyzer would have to generate runtime-specific output directly, multiplying its complexity by the number of targets. This approach optimizes for the demo and sacrifices the architecture.

The second approach is the **abstract-IR-plus-compiler** model, which is the architecture the vision document already gestures toward. Agents, subagents, skills, and instructions are authored once in a neutral format (a `murmur/` directory of Markdown-plus-frontmatter files governed by a typed schema). A compiler with one pluggable adapter per runtime translates that intermediate representation into each target's native layout. The codebase analyzer produces only neutral skills and instructions, never runtime-specific files, so its complexity is independent of the number of targets. The advantage is that this is the only model that genuinely delivers compile-once/emit-many, keeps knowledge externalized by construction, and makes adding a runtime an O(1) effort of implementing a single `RuntimeCompiler` interface. The cost is higher up-front engineering: the schema must be designed carefully, the compiler needs a real adapter abstraction, and there is a risk of over-engineering the IR before any runtime has validated it. This is a manageable risk if the first milestone deliberately implements two structurally dissimilar targets (Copilot's persona-Markdown and goose's parameterized-recipe paradigm) to stress the abstraction early.

The third approach is a **protocol-first / ACP-native** model, in which Murmuration targets the Agent Client Protocol as its primary output and treats per-runtime file formats as secondary exports. This is the most future-proof option and aligns with where the industry is heading, but it is premature: ACP's remote-agent support is still a work in progress, the user's entire existing investment is in Copilot's file-based customization system, and betting the first release on a still-maturing protocol would delay any usable output. ACP belongs on the roadmap as a later compile target, not as the foundation.

A cross-cutting decision concerns the **master agent and dynamic spawning**. The spawn heuristic could be hardcoded (deterministic mappings from task keywords to skill sets), example-driven (the master agent loads a skill that teaches it how to write agent definitions), or LLM-generated each time (the master drafts the subagent definition from the task description using the host model). The LLM-generated option is the most flexible and the least deterministic; the example-driven option is the sweet spot, because it externalizes the spawning logic itself into a skill — which is perfectly consistent with the framework's core principle that all knowledge lives in skills — while still grounding the master agent in concrete patterns rather than free improvisation.

## 6. Recommended Approach

The recommendation is the abstract-IR-plus-compiler model, with the master agent's spawning logic externalized into a skill, two structurally dissimilar compile targets in the first milestone, and ACP deferred to the roadmap. This is the only approach that satisfies the brief's non-negotiable property — generic agents with all knowledge externalized — as a structural guarantee rather than a convention that erodes over time. The two initial targets are deliberately chosen to stress the abstraction across the two genuinely different paradigm families, and they are Copilot and goose. Copilot and Claude Code, despite the earlier framing, share the same substrate — Markdown body plus YAML frontmatter, named-persona agents, description-driven delegation, per-agent tool and model fields — and the existing-patterns research found the user's `.agent.md` schema near-isomorphic to Claude Code subagents; compiling between two near-isomorphic formats would prove little and risk an IR that is merely "Copilot frontmatter with field renames." goose, by contrast, uses a structurally different recipe model — YAML with typed Jinja parameters, `sub_recipes`, `extensions`/`available_tools`, `retry`, and `response.json_schema` — so an IR that compiles cleanly to both a persona-Markdown runtime and the goose recipe paradigm is genuinely validated. Claude Code becomes a near-free third adapter for the spawning demonstration, but it is explicitly not one of the two validation targets and moves to Phase F.

To manage the principal risk of this approach — over-engineering the schema before any runtime validates it — the build sequence is deliberately validation-first. The very first implementation milestone hand-authors a tiny set of abstract definitions (one master agent, three generic agents, two skills, one instruction) and writes the Copilot and goose adapters against them, before the analyzer or any other command exists. Only once round-trip compilation works for both targets does the schema freeze and the remaining commands get built on top of it. This inverts the temptation to build the analyzer first (which is the most exciting piece) and instead de-risks the foundation. The spawn heuristic is delivered as a `subagent-authoring` skill that the master agent loads, encoding the rules for which skills to attach, which instructions are relevant, what tools to allow, and how to phrase the role description — keeping the master agent itself generic. The publish step is treated as a first-class defense-in-depth safety layer with a mandatory `--dry-run` diff and a `--strict` mode that fails the publish when any high-entropy or known-secret-pattern string survives, directly addressing the real-world token-leak risk the user already experienced in this very session while explicitly disclaiming any guarantee of completeness.

## 7. Architecture & Design

The heart of the system is the **abstract intermediate representation**, stored in a `murmur/` directory at the project root. It contains four kinds of definition. Agents live in `murmur/agents/` and carry a neutral frontmatter — name, role description with a `"Use when"` trigger, allowed-tool tags, a list of referenced skills, a list of referenced instructions, and an optional preferred-model hint — over a generic prose body that must contain no project facts. Subagents live in `murmur/subagents/` and additionally carry spawn metadata used by the master agent. Skills live in `murmur/skills/`, each as a `SKILL.md` (flat) or a `<skill-name>/SKILL.md` directory (when assets are needed), carrying a name and description and a knowledge body; skills are where all codebase-specific content legitimately lives. Instructions live in `murmur/instructions/` with an `applyTo` glob and a rules body. A typed `murmur.config.ts` (with JSON fallback) declares enabled compile targets, project metadata, plugin registration, and the publish scrubbing rules. This layout maps one-to-one onto the user's existing Copilot conventions, which the analyst confirmed, so the mental model transfers directly.

The **compiler** is a registry of adapters, each implementing a `RuntimeCompiler` interface with `compileAgent`, `compileSkill`, and `compileInstruction` methods plus an asset-resolution strategy. The Copilot adapter emits `.github/agents/*.agent.md`, `.github/instructions/*.instructions.md`, and skill files in the locations Copilot discovers; the goose adapter emits recipe YAML with typed parameters, `sub_recipes`, declared `extensions`/`available_tools`, and `response.json_schema` plus AGENTS.md parity, which is the structurally different paradigm that validates the IR; later adapters (Claude Code, Cursor, ACP) implement the same interface. Adapters degrade gracefully: on a runtime that lacks subagents, the compiler can flatten subagent logic into the master agent rather than failing. Compile output is written atomically — each target's files are assembled in a staging directory and moved into place only when the full target compiles successfully, so a mid-compile failure never leaves a half-written `.github/agents/` tree. Asset references inside skills are resolved per-adapter (copy-alongside for file-based runtimes), and the abstract schema permits assets but the first version may restrict them to keep resolution simple.

The **master agent** is a dedicated generic orchestrator shipped in the base library, and it is important to be precise about where its behavior lives: dynamic spawning is an in-runtime behavior encoded in the shipped `subagent-authoring` skill plus the generic master-agent body, not a CLI command — the deterministic `bun` process is not involved in any spawn at runtime. The master agent decomposes a task, consults a registry of available subagents, and matches subtasks to specialists. When no specialist fits, it loads the `subagent-authoring` skill, drafts a scoped subagent definition (attaching the skills and instructions that skill's rules indicate, restricting tools, and writing a focused role description), and invokes it through the host runtime's subagent protocol. There are two invocation paths depending on a runtime capability that must be empirically established rather than assumed. When the target runtime hot-loads newly written agent definitions mid-session, the master writes the definition to a temporary location and dispatches it by name; when it does not, the master degrades to composing an in-context ephemeral persona — an inline role description with the relevant skills and instructions passed directly in the subagent prompt — rather than writing a file the runtime must rediscover. Whether a given runtime supports hot-load is determined by the Phase A.5 capability probe, and the persisted-versus-ephemeral decision (persist to `murmur/subagents/` only when the same specialist is needed more than twice in a session) applies in either path. This keeps the master agent itself free of project knowledge while giving it a principled, externally-defined spawning procedure that works regardless of the runtime's discovery lifecycle.

The **init codebase-analyzer** must be specified honestly, because a deterministic `bun` CLI cannot summon the LLM running inside the user's IDE — the dependency arrow points from agent to tool, never the reverse, so the earlier "runs the analyzer inside the host runtime with no API key" framing is corrected here. `init` is split into two passes. The structural pass is the default and always runs: it is pure static analysis in `bun` that parses `package.json`, `tsconfig.json`, the directory tree, lockfiles, test configuration, and CI workflow files, and from these emits neutral structural skills (project structure, build system, test conventions) and `applyTo`-scoped instructions (language conventions). It needs no LLM, no API key, and no network, so the "no separate API key" claim is literally true for this path and the two-minute budget is trivially met. The optional semantic pass enriches the structural output with knowledge that requires an LLM, and there are two concrete invocation models for it. The first is the agent-invoked model: Murmuration ships a `murmur-init` agent/skill that the user runs from inside their own host agent (Copilot, Claude, or goose), and that agent calls the CLI's structural pass and then authors the semantic skills using the IDE LLM it already has — the LLM is the caller and the CLI is the callee, which respects the real control flow and incurs no separate credential. The second is the headless-CLI model: when an installed headless agent binary (`claude`, `goose`) is present and authenticated, `init --semantic` shells out to it with a generated prompt and ingests the result; this is feasible but per-runtime, network-dependent, and consumes the user's own subscription, so it is offered as a fallback rather than the default. The recommended model is agent-invoked, because it matches the actual dependency direction, requires no extra binary, and keeps the deterministic path free of any LLM dependency. The analyzer is idempotent in both passes: re-running prompts to merge, overwrite, or cancel, defaulting to merge.

The **publish step** is reframed from a safety guarantee into a defense-in-depth layer: it reduces the chance of a leak but never eliminates it, and the documentation and CLI output both state that the user owns final verification. It reads `murmur/` and writes a scrubbed copy to a separate directory, replacing the detected repository name with a placeholder, stripping user-specific path prefixes, redacting configured domain terms, and masking email and name PII. Crucially, redaction is not limited to a user-maintained denylist, because a denylist always misses what the user forgets to enumerate; the scrubber additionally runs entropy-based and pattern-based secret scanning using established gitleaks-style rulesets to catch high-entropy blobs, JWTs, and known token formats that no configured list would name. The `--dry-run` flag shows the scrub diff without writing anything, and `--strict` is given a single coherent meaning: the publish fails if any high-entropy string or known-secret-pattern match survives anywhere in the output, with an explicit allowlist override for strings the user has confirmed are generic. This resolves the earlier self-contradiction of "erroring on the unrecognized." Because `murmur.config.ts` is executable TypeScript, importing it runs arbitrary code, so loading an untrusted repository's config is a code-execution vector; the publish and compile paths therefore use a constrained config loader that defaults to the JSON form for untrusted contexts and requires an explicit `--allow-config-exec` flag before executing the TypeScript form. The **CLI** is a thin bun-bundled binary (`dist/cli.js` with a shebang, linked through the `bin` field) dispatching to these command modules, with `doctor` validating schema correctness, reference integrity, and glob syntax before any compile or publish runs.

## 8. Implementation Plan (Phased)

**Phase A — Foundation and schema validation.** Before writing any command, hand-author a minimal set of abstract definitions (the master agent, three generic agents drawn from the recurring ten-agent archetype, two skills, one instruction) and a typed schema with a runtime validator. Then implement the `RuntimeCompiler` interface and two structurally dissimilar adapters — Copilot (persona-Markdown) and goose (parameterized recipe) — and prove that the hand-authored IR compiles to valid output for both. This phase ends when both targets produce schema-valid files and the abstraction has survived contact with two genuinely different runtime paradigms rather than two near-isomorphic Markdown formats. The schema freezes here.

**Phase A.5 — Runtime capability probe.** Before committing to dynamic spawning, run a one-page empirical probe per target runtime that determines whether an agent can write a new subagent definition mid-session and dispatch it within the same session — that is, whether the runtime hot-loads dynamically written agent files. This is currently unverified for Copilot and Claude and must be measured, not assumed. The probe's result is recorded and gates Criterion 3: if a runtime hot-loads, the file-writing spawn path is used; if it does not, the master agent falls back to the in-context ephemeral-persona path described in section 7. No phase that depends on spawning proceeds on an unproven hot-load assumption.

**Phase B — CLI skeleton and core commands.** Build the bun-bundled CLI entry point with subcommand routing, `--help`, and friendly no-argument behavior. Implement `compile --target`, `doctor` (schema, reference integrity, glob syntax), and `list`. Wire the Phase A compiler behind `compile`. This phase delivers a usable tool for someone who hand-writes their `murmur/` directory.

**Phase C — The init analyzer.** Implement the deterministic structural pass of `init` first: pure `bun` static analysis of `package.json`, `tsconfig.json`, the directory tree, lockfiles, test config, and CI files that generates the structural portion of the `murmur/` directory with no LLM, and handle the merge/overwrite/cancel prompt on re-run. Then ship the optional semantic pass as the `murmur-init` agent/skill that the user runs from inside their host agent (agent-invoked model), with the headless-CLI shell-out as a fallback when a `claude` or `goose` binary is present. Validate the structural path against the success criterion of producing its generic agents, skills, and scoped instructions on a moderate Node/TypeScript project in under two minutes; the semantic enrichment is validated separately and is not bound by the two-minute deterministic budget.

**Phase D — Master agent spawning.** Author the `subagent-authoring` skill and implement the master agent's match-or-spawn loop, selecting the file-writing or ephemeral-persona path according to the Phase A.5 probe result and including the temporary-versus-persistent decision. Demonstrate the two required spawn scenarios (a data-validator and a config-migrator) end to end on at least one runtime whose probe result is known.

**Phase E — Publish and packaging.** Implement `publish` with the scrubbing rules, `--dry-run`, and `--strict`; implement `add agent|subagent|skill|instruction` scaffolders. Finalize packaging: the `build` script bundling to `dist/cli.js`, correct `files` and `bin` fields, a sub-ten-megabyte tarball verified with `bun pack`, a `CHANGELOG.md`, and the `docs/COMPARISON.md` synthesis document. Resolve `gh` authentication, push to the private remote, and add CI.

**Phase F (roadmap) — Additional runtimes and global commands.** Add the Claude Code, Cursor, and ACP adapters; implement the deferred global-command surface; and deepen the semantic-depth analysis of the init analyzer. Claude Code is a near-free third adapter (it shares Copilot's persona-Markdown substrate) and is valuable for the spawning demonstration, but it is explicitly not a validation target. These are all post-v0.1.0.

## 9. Test Plan

Testing maps directly onto the ten success criteria, with each criterion becoming an executable assertion. Schema and compiler correctness is covered by golden-file tests: the hand-authored IR from Phase A compiles to fixtures that are byte-compared (or schema-validated) for both the Copilot and goose targets, so any regression in an adapter is caught immediately, and because goose's recipe paradigm is structurally unlike Copilot's persona-Markdown, these golden files genuinely exercise the abstraction rather than a field-rename. A separate atomicity test deliberately fails an adapter mid-compile and asserts that no partial output is left in the target tree, proving the staging-then-move strategy. The knowledge-externalization guarantee — the framework's reason to exist — is enforced by a dedicated scanner test that reads every file in `murmur/agents/` and asserts zero matches against codebase-specific patterns (absolute `/Users/` paths, the repository name, known domain terms), while separately asserting that at least eighty percent of project-specific terms appear in skills and instructions. This test runs in CI and is treated as a hard gate.

The `doctor` command is tested in both directions: a freshly initialized project must report zero errors with exit code zero, and a deliberately corrupted fixture (a missing referenced skill, malformed YAML frontmatter, an invalid `applyTo` glob, a circular subagent dependency) must report each error with a clear description and file path and a non-zero exit code. The `init` analyzer is validated against a representative Node/TypeScript fixture project for structural-output completeness and the two-minute time budget on the deterministic path, with the merge/overwrite/cancel branch exercised by re-running; the semantic pass is validated separately and is not held to the deterministic budget. Master-agent spawning is covered by the two scenario tests, asserting that a valid, readable subagent is produced and invoked via whichever path the Phase A.5 probe selected. The `publish` scrubber is tested with a fixture carrying known sentinel values (repository name `test-project`, domain term `proprietary-feature`, a fake email) and asserts the output contains the placeholders but none of the originals, that the source directory is untouched, and that `doctor` passes on the scrubbed output; `--dry-run` is asserted to mutate nothing. Critically, a false-negative test is added to cover the real risk: the fixture also embeds a high-entropy secret-shaped string that appears in no configured denylist, and the test asserts that `--strict` flags or fails on it via the entropy/pattern scanner, proving the scrubber does not silently pass unknown secrets. A separate security test confirms that loading a `murmur.config.ts` containing executable code does not run that code unless `--allow-config-exec` is passed. Packaging is validated by running `bun pack`, asserting the tarball contains only intended files and is under ten megabytes, then installing it into a scratch directory and smoke-testing every command's `--help`. Functional in-runtime execution (actually running compiled agents inside Copilot or Claude) is explicitly out of scope for v0.1.0 — schema validity is the acceptance bar — and is noted as a roadmap item to avoid the cost of automating live runtime environments in CI.

## 10. Risks & Mitigations

The largest feasibility risk is the **analyzer invocation model**: a deterministic CLI cannot call the IDE's host LLM, so any design that assumes it can is unbuildable. The mitigation is the structural/semantic split in section 7 — the default structural pass needs no LLM and is therefore always feasible, while the optional semantic pass uses the agent-invoked model (the user's host agent calls the CLI, respecting the real dependency direction) with a headless-CLI fallback. The second feasibility risk is **runtime hot-load**: runtimes may not invoke a subagent definition written mid-session, which would silently break dynamic spawning. The mitigation is the Phase A.5 capability probe that empirically establishes hot-load per target and gates Criterion 3, plus the in-context ephemeral-persona degradation path when hot-load is unavailable. The third risk is **schema over-engineering** — designing an elaborate intermediate representation that later proves awkward for a real runtime. The mitigation is the validation-first sequence in Phase A: two structurally dissimilar adapters (Copilot persona-Markdown and goose recipe) must compile the hand-authored IR before the schema freezes, so the abstraction is proven against genuinely different paradigms rather than two near-isomorphic Markdown formats. The fourth risk is **analyzer non-determinism and token limits** in the semantic pass: because it runs inside a host LLM, its output varies and a large codebase can exceed context. The mitigation is to scope v0.1.0 to the deterministic structural pass for the acceptance bar, treat semantic extraction as optional enrichment, and have the semantic pass sample representative files and chunk when necessary. The fifth risk is **incomplete scrubbing on publish** leading to leaked proprietary terms or secrets — a risk made vivid by the live GitHub token this session found exposed in the user's `.env`. The mitigation is to treat publish as defense-in-depth rather than a guarantee: pair the configured denylist with entropy/pattern-based gitleaks-style secret scanning, make `--strict` fail on any surviving high-entropy or known-secret match with an allowlist override, sandbox the executable `murmur.config.ts` behind `--allow-config-exec`, and document explicitly that the user owns final verification. The `.env` token itself is a `.gitignore` and secret-hygiene problem that publish does not and should not pretend to solve.

A sixth, market-level risk is **weak differentiation**: since goose has subagent delegation via `summon` and ECC.tools already does repo-to-skills, Murmuration cannot honestly claim to have invented any single capability. The mitigation is to position on two clearly separated tiers and to document them honestly in `docs/COMPARISON.md` rather than overclaiming. The shipped v0.1.0 differentiator is the only local, open-source tool combining deterministic structural auto-init, compile-once/emit-many across two structurally-different runtime paradigms, knowledge externalization enforced by a CI gate, and a defense-in-depth publish scrubber. The aspirational v1.0 differentiator additionally adds ACP protocol portability, spawnable specialists proven across runtimes, and semantic init. Keeping the launch claim distinct from the roadmap claim avoids leaning on capabilities (ACP, a leak-proof scrubber) that are deferred or imperfect at launch. A seventh risk is **runtime drift**: target formats (Copilot frontmatter, goose recipes, Claude subagent schema) evolve, and adapters can silently break. The mitigation is golden-file tests per adapter and treating each adapter as independently versioned. Finally there is an **operational risk** around the blocked `gh` authentication and the exposed token; the immediate mitigation is to revoke the token, re-authenticate `gh` via its own secure flow, and never let Murmuration handle raw credentials.

## 11. Open Questions & Decisions

The brief raised ten open questions; the recommended resolutions are as follows. **Second target runtime** — choose goose over Claude Code, because goose's recipe model (typed Jinja parameters, `sub_recipes`, `extensions`, `response.json_schema`) is structurally different from Copilot's persona-Markdown and therefore actually stresses the IR, whereas Claude Code is near-isomorphic to Copilot and would validate little; Claude Code follows in Phase F as a near-free third adapter for the spawning demonstration. **Master agent identity** — it is a dedicated generic orchestrator shipped in the base library and included by default on `init`, not an overloaded reuse of the existing architect; this keeps its role unambiguous. **Spawn heuristic** — externalize it into a `subagent-authoring` skill (example-driven), consistent with the framework's principle that knowledge lives in skills, rather than hardcoding or fully free-form LLM generation, with the file-writing-versus-ephemeral path chosen by the Phase A.5 probe. **Init analyzer depth** — v0.1.0's acceptance bar is the deterministic structural pass only (no LLM); the optional semantic pass is agent-invoked enrichment and full semantic extraction is a Phase F deepening, protecting the two-minute budget and respecting the real CLI-to-LLM dependency direction. **Publish verification** — ship a `--dry-run` diff and a `--strict` mode that fails on any surviving high-entropy or known-secret-pattern string via gitleaks-style scanning; publish is defense-in-depth and the user retains final responsibility.

**Skill assets** — permit the directory-structured form in the schema but restrict v0.1.0 skills to single-file `SKILL.md` to avoid per-runtime asset-resolution complexity; revisit when a concrete asset need appears. **Global command scope** — v0.1.0 implements project-level commands fully and ships only a minimal global surface (`list` of globally installed packs); full global operations are a later milestone, and running project commands without a `murmur/` directory produces a clear "run `murmur init` first" error. **Compiler plugin registration** — start with TypeScript adapter files registered in `murmur.config.ts` for simplicity and portability; an npm-package plugin model with auto-discovery is a later option once the interface is stable. **ECC.tools and Hermes evaluation** — keep them in `docs/COMPARISON.md` but label the analysis explicitly as based on public materials only, since their internals are not accessible; this preserves the document's credibility. **Multi-runtime test coverage** — schema validation is sufficient for v0.1.0; functional in-runtime execution is deferred to avoid the cost of automating live agent environments in CI.

## 12. Execution Guidance & Sequencing

Execution should follow the phase order strictly, because each phase de-risks the next. The single most important discipline is to resist building the init analyzer first despite its appeal; the schema and the two adapters must come first, or the project risks generating output for an abstraction that has never been validated. Within Phase A, author the smallest possible IR that exercises every schema feature (an agent that references a skill and an instruction, a subagent with spawn metadata, a flat skill, and an `applyTo` instruction) so the adapters are forced to handle the full surface early. Freeze the schema only when both adapters pass golden-file tests, and from that point treat schema changes as breaking changes requiring a version bump and adapter review.

The immediate next physical actions, before any of the build phases, are operational and security-related: revoke the GitHub token exposed in the user's `.env`, re-authenticate `gh auth login`, confirm `.env` is git-ignored in every project, and only then create and push the private `murmur` remote. The repository already has its scaffold commit, so the first build milestone (Phase A) becomes the second commit, satisfying the two-commit hygiene criterion. Definition of done for v0.1.0 is the conjunction of the ten success criteria with three treated as non-negotiable gates: the knowledge-externalization scanner reporting zero project facts in agent bodies, `doctor` passing on freshly initialized output, and the publish scrubber proven against both sentinel values and an unlisted high-entropy secret with the source left untouched. Anything not meeting those three gates is not a release regardless of other progress. The `docs/COMPARISON.md` document should be written last, once the implemented feature set is known, so it describes what Murmuration actually does rather than what it aspired to — and it should state the two-tier differentiator (the shipped v0.1.0 union of deterministic structural auto-init, compile across two structurally-different paradigms, CI-enforced externalization, and defense-in-depth publish, kept distinct from the aspirational v1.0 union that adds ACP, cross-runtime spawnable specialists, and semantic init) rather than overstating novelty.
