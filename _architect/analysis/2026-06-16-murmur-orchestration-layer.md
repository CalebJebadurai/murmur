## 1. Executive Summary

Murmuration v0.1.0 succeeded at a narrow, well-defined job: it authors agent definitions — agents, subagents, skills, and instructions — once in a neutral intermediate representation and compiles them to multiple runtimes through a pluggable adapter. But the survey of the user's own projects revealed that the single most valuable artifact they possess is not a set of agent definitions; it is the *orchestration* encoded in `architect.agent.md` — a governed, multi-phase pipeline with branches, tiers, selective-dispatch decision tables, parallel-execution caps, hard loop limits, multi-dimensional scoring rubrics, output-section contracts, and run-log execution tracking. That orchestration is the genuine intellectual property of the setup, and today it is trapped inside a hand-written Copilot agent that cannot be reused, validated, ported to another runtime, or audited in a controlled way. Murmur cannot represent it, cannot compile it, and cannot govern it. Closing that gap is the highest-value addition on the roadmap.

The durable moat is the **portable orchestration IR**: the compile-once-target-many representation that turns a hand-written architect agent into a validated, version-controlled, runtime-neutral source of truth. This is what no competitor offers — goose and Claude Code *execute* but do not *compile portably*; murmur would compile portably. The recommended approach therefore leads with the IR and the compiler and treats execution as explicitly secondary. Concretely: keep the compiler as the immovable core of murmur's identity; add a fifth IR type for pipelines (with branch-aware phase sequences and a classification/routing step), plus first-class rubrics (with weighted multi-rubric aggregation and conditional dimensions) and instruction-level output contracts; and add `murmur run` as an **optional, clearly-secondary convenience driver** that can shell out to a host agent CLI the user already has — never an embedded LLM engine. The compiler is the product; `murmur run` is a dev-loop convenience layered on top.

Two honest framings govern the rest of this plan. First, `murmur run`'s host-CLI subprocess execution is a **net-new capability and code-execution surface with no precedent in the v0.1.0 codebase** — there is zero subprocess spawning in murmur today, and the init command does the opposite of driving anything (it emits an agent that the *user* invokes inside the host runtime, so the host LLM calls the CLI, never the reverse). `run` is therefore the riskiest, most novel part of the roadmap and is scoped accordingly: opt-in, gated, and targeting only the `claude` and `goose` CLIs (Copilot has no headless CLI, so Copilot users always get compile-and-instruct, never local execution). Second, what murmur can *deterministically* govern is a deliberately narrow set: it owns iteration-counting against hard caps, subprocess concurrency-capping, rubric *arithmetic* computed from numbers the host supplies, and RUN-LOG formatting. The *decisions* — which agents to dispatch, when a natural-language early-exit condition is satisfied, what score each dimension earns — are generative and remain the host LLM's job. The work is staged across six milestones (v0.2 pipeline IR and an optional `run`; v0.3 rubrics and output contracts; then v0.4–v0.7 gated on adoption signal: dispatch tables and a classifier; a concurrency engine ported from the audio2text worker model; additional adapters and a plugin model; and project/DX hardening). The expected outcome is that murmur becomes the only local, portable system that can *define, compile, and validate* multi-agent pipelines — with optional, best-effort local execution as a convenience, not the headline.

## 2. Problem Statement & Context

The central asset is `/Users/cnickson/projects/personal/.github/agents/architect.agent.md`. It is not a single agent so much as a compiled-by-hand orchestration program. It defines a hub-and-spoke topology with a fifteen-agent roster; a selective-dispatch model expressed as decision tables whose columns are “agent / invoke when / skip when”; a parallel-dispatch table capping concurrency per pattern (three Explore agents, two research streams, critic-and-planner never parallel); a hard loop-limits table (critic↔planner one-to-three iterations with an early-exit condition, research-critic↔planner one-to-two, single-callback caps); and a discipline of writing every artifact into an `_architect/` directory. Crucially, it is not a single linear phase list: it is two distinct branches selected by a classification gate. A **CODING** branch runs Phase 0→0b→1→2→3→4→5→5b (with a conditional 5c), and a separate **RESEARCH** branch runs Phase 0→R1→R2→R3→R4→R5→R5b; the classification step at Phase 0b routes between them, and the three pipeline tiers (lightweight, standard, extended) each select a *subset* of phases *within* the chosen branch. Companion agents extend this with a multi-rubric scoring model: the critic encodes an eleven-dimension technical scorecard out of fifty-five with mandatory and conditional dimensions and a one-to-five scale, while the business-critic and social-critic each add a forty-point scorecard, and the three combine into a weighted multi-critic total (the RUN-LOG records aggregates like `105/130` and `106/135`). The agri project's `_architect/RUN-LOG.md` records each execution as a table row — date, topic slug, tier, iterations, total score, verifier verdict, notes. None of this — neither the dual-branch routing nor the weighted multi-rubric aggregation — is representable in murmur's current IR.

Murmur today, at `/Users/cnickson/projects/personal/murmur`, models four IR kinds in `src/schema/` and compiles them through the `RuntimeCompiler` interface in `src/compiler/RuntimeCompiler.ts` to two adapters (`copilot.ts`, `goose.ts`), driven by atomic staging in `compile.ts` and gated by `doctor.ts`. The analyst confirmed that adding a fifth “pipeline” kind is mechanically straightforward — a new schema file, a `validatePipeline` function, a glob in `load.ts`, a `pipelines` field on the `IRSet`, reference-integrity checks in `runDoctor`, and an optional `compilePipeline` method on the adapter interface. The deeper challenge is threefold. First, the orchestration constructs are structurally rich (phases containing dispatch tables containing invoke/skip predicate lists, plus loop and parallelism tables), and the minimal zero-dependency frontmatter parser cannot ingest arrays-of-maps and will silently mis-parse out-of-subset data, so pipeline data must live in the document body as pure YAML rather than in frontmatter. Second, runtimes differ wildly in what orchestration they can express — Copilot has `runSubagent` and an architect persona, goose has `sub_recipes` with sequencing, and Cursor has effectively neither — so the compiler needs a principled per-runtime degradation rule. Third, and most consequentially, `murmur run` raises an identity question: executing a real governed pipeline requires an LLM to drive each phase, which would reintroduce exactly the dependency-direction problem that v0.1.0's init analyzer was carefully designed to avoid.

## 3. Research Findings

The analyst's investigation produced four findings that shape the entire design. The first is that the IR extension is genuinely mechanical: the `IRSet` in `src/schema/index.ts` gains a `pipelines` array, `load.ts` gains a glob for `murmur/pipelines/*`, a new `validatePipeline` mirrors the existing validators, `runDoctor` reuses its existing `checkRefs` set-membership pass and `findCircular` depth-first search for the new references, and `emitAll` in `RuntimeCompiler.ts` gains an optional `compilePipeline` call that adapters may decline to implement. Nothing about the schema or compiler architecture resists the addition; the existing patterns extend cleanly.

The second finding is the binding technical constraint. The hand-written `parseFrontmatter` in `src/util/frontmatter.ts` supports only scalars, inline arrays, and block arrays of scalars — it cannot parse arrays of maps, and crucially it does so *silently*, mis-parsing rather than erroring. The YAML *emitter* is more capable than the *parser*. The practical consequence is that the structured heart of a pipeline (branches with nested phase and dispatch tables) must be authored as YAML in the document body, never crammed into the `---` frontmatter block. Because hand-parsing arbitrary nested, indentation-sensitive YAML would amount to reimplementing a YAML parser — the very silent-mis-parse failure mode the zero-dependency stance was trying to avoid — this plan does **not** propose a permissive "extended reader." Instead it constrains the pipeline body to a strict, minimal, formally-specified YAML subset and makes the reader **hard-error (PARSE-ERROR) on anything outside that subset**, so a malformed or out-of-subset body fails loudly at the file-and-line level rather than mis-parsing into wrong governance. This is a design constraint, not a blocker, and it keeps the zero-dependency promise intact while eliminating the silent-mis-parse single point of failure (the trade against vendoring one tiny vetted YAML dependency is weighed explicitly in section 7).

The third finding is the recommended answer to the central architectural question. The analyst evaluated four approaches — a pure declarative compiler, an embedded LLM execution engine, a hybrid of compiler-plus-thin-driver, and compile-only syntactic sugar — and recommended the hybrid. In it, compilation remains the core (a pipeline compiles to a Copilot master agent or a goose recipe), and `murmur run` is an opt-in local driver that uses `Bun.spawn` to invoke a host agent's own CLI, with no embedded LLM, degrading to a “compile-and-instruct” mode where no such CLI exists. It is important to state plainly what this *is not*: it is **not** a reuse of any existing pattern in murmur. The analyst confirmed there is zero subprocess spawning anywhere in `murmur/src` today, and the init command is the opposite of a driver — `initCommand` runs the pure `analyzeStructural` pass and lays down a `murmur-init` agent that the *user* invokes inside their host runtime, so the dependency direction is murmur → artifact → host-LLM-calls-CLI, never murmur → CLI. `murmur run`'s subprocess execution therefore *inverts* that direction (murmur becomes the active driver) and introduces an entirely new code-execution surface. This is the single largest new risk in the roadmap, and the hybrid is justified on its own merits — it keeps the deterministic CLI from ever embedding a model — not by appeal to a precedent that does not exist. The fourth finding concerns placement: scoring rubrics are reusable enough across agents and projects to deserve their own first-class IR kind under `murmur/rubrics/` with a `murmur score` command, whereas output-section contracts are naturally an *extension* of the existing `InstructionDefinition` (an optional ordered `sections` field) enforced by the existing doctor pass rather than a new kind. The analyst also confirmed the concrete data to model from the sources: the exact dual-branch phase lists and tier subsets from `architect.agent.md`, the weighted multi-rubric scorecard structure from the critic agents, the RUN-LOG column format from `agri/_architect/RUN-LOG.md`, and the `effective_workers = min(configured, rpm, tpm, n_tasks)` worker-budget algorithm with retry-and-backoff from the audio2text Gemini backend.

## 4. Goals, Non-Goals & Constraints

The goals are organized by milestone. For v0.2, murmur must model a pipeline as a fifth IR kind capturing phases, per-phase agent dispatch, gating conditions, loop limits with hard caps, parallelism caps, and tiers; compile it to a Copilot master agent and a goose recipe; and provide `murmur run` as an optional local driver that executes a pipeline by shelling to a host agent CLI and emits a `RUN-LOG.md` matching the agri format. For v0.3, murmur must model scoring rubrics as a first-class IR kind validated by `doctor` and checkable by a new `murmur score`, and extend instructions with an enforced ordered-section contract. For v0.4, agent frontmatter must carry machine-readable invoke-when/skip-when dispatch tables, a `murmur classify` command must select an agent set by task type, and the base library must ship a domain-critic roster (business-critic, social-critic, data-critic, fact-checker, verifier) as generic templates. For v0.5, the `run` driver must gain a worker pool with budget enforcement and retry-with-backoff. For v0.6, murmur must add Claude Code, Cursor, and ACP adapters plus an npm-package plugin model and skill assets. For v0.7, murmur must generate a `lefthook.yml` and agent CODEOWNERS, expose schema-driven validation for plugin authors, and provide a `murmur docs` HTML compiler.

The non-goals preserve coherence. Murmur is still not an agent runtime: even with `run`, it never embeds an LLM, never makes model API calls itself, and always delegates actual agent execution to a host CLI it spawns. It does not add runtime dependencies — the worker pool, YAML reader extension, and run driver are all hand-written on bun primitives. It does not guarantee that every runtime can express every orchestration construct; adapters degrade gracefully and declare what they drop. It does not retroactively convert the user's existing hand-written architect agents (though they are the reference the pipeline IR must be able to round-trip). The constraints are firm and inherited from v0.1.0. The schema froze at v0.1.0, so the pipeline addition is additive and must not break the four existing kinds or their golden-file fixtures. The frontmatter parser's limitation dictates that structured pipeline data lives in the body. The `run` driver must never mutate source and must run fully offline on its deterministic paths (compile, doctor, score, classify), reserving network and LLM access strictly for the explicitly-invoked, host-CLI-delegated execution path. And the central tension — that adding `run` risks eroding the “compile, don't execute” identity — is resolved by making execution opt-in, delegated, and clearly secondary to compilation rather than a peer capability.

## 5. Analysis of Approaches

The defining decision is what `murmur run` *is*, and four approaches span the space.

The first is the **pure declarative compiler**. Murmur models pipelines in the IR and compiles them to each runtime's native orchestration form, but ships no `run` command at all — execution is entirely the host runtime's job. The strength is purity: it is a perfect extension of the v0.1.0 identity, adds zero execution surface, keeps everything offline and dependency-free, and is the least code. The weakness is that it under-delivers on the roadmap's headline promise. The user explicitly wants `murmur run` and a `RUN-LOG.md`; a compiler that emits an architect agent but cannot itself execute a governed loop leaves the most compelling capability — local, portable, governed execution with recorded scores — on the table. It also forfeits the loop-limit and parallelism *enforcement* that only an actual driver can guarantee; compiled prose tables are advisory, and a host LLM may ignore them.

The second is the **embedded LLM execution engine**. Murmur's `run` command becomes a real orchestrator: it loads the pipeline, drives each phase, calls an LLM to evaluate dispatch predicates and produce agent outputs, scores against rubrics, and enforces loops and caps in process. This maximally delivers governance — murmur would *truly* enforce the one-to-three critic loop and the parallelism caps. But it shatters both founding constraints. It requires an LLM SDK (a runtime dependency and an API key), it reintroduces the dependency-direction problem the init analyzer solved (the deterministic CLI would now be the caller of the model), and it duplicates what the host runtimes already do well. It turns murmur into a competing agent runtime, which is an explicit non-goal and a far larger maintenance surface.

The third is the **hybrid: compiler core plus thin local driver**. Compilation is unchanged as the core; `murmur run` is an optional driver that does the deterministic orchestration bookkeeping itself — sequencing phases, counting iterations against the loop caps, capping concurrent subprocesses via a local worker pool, computing rubric arithmetic from host-supplied numbers, and writing the RUN-LOG — while delegating every actual agent turn by `Bun.spawn`-ing a host agent's CLI. This subprocess-spawning is a **net-new code-execution surface**: there is no `Bun.spawn` or child-process usage anywhere in murmur v0.1.0, and it inverts the init dependency direction (init emits an artifact the host invokes; here murmur becomes the active caller). It is justified not by precedent but by what it buys — real enforcement of the *mechanical* parts (iteration ceilings, subprocess concurrency caps, RUN-LOG structure) without ever embedding a model — and it realistically targets only the `claude` and `goose` CLIs, since Copilot has no headless CLI to spawn. Murmur never embeds an LLM; it shells to `claude`, `goose`, or a configured command, captures structured output, and computes rubric scores *only where the host emits machine-readable numbers* to compute from. Where no host CLI is available (notably every Copilot user), `run` degrades to “compile-and-instruct”: it emits the orchestrator and prints the exact steps the user should run. Its honest cost is twofold: it adds the riskiest new surface in the roadmap (subprocess execution and untrusted-output parsing), and its governance is *thin* — the decisions that actually matter for the reference fixture (which agents a natural-language predicate selects, whether a prose early-exit condition like “all dimensions ≥ 4” is met, what numeric score each dimension earns) are generative and stay with the host LLM. Murmur enforces the caps and computes the arithmetic; it does not make the judgments.

The fourth is **compile-only syntactic sugar** — like the first, but `run` exists purely as an alias that compiles and then prints instructions, with no bookkeeping. It is cheap but barely more than the declarative compiler and gives up the deterministic enforcement the hybrid uniquely offers.

A secondary axis is **where rubrics and contracts live**. Rubrics could be a sub-kind of skill, but they are referenced by multiple agents, reused across projects, and consumed by a dedicated `score` command, so a first-class `rubric` kind is cleaner. Output-section contracts could be a new kind, but they are intrinsically a property of an instruction (“documents under this glob must contain these ordered sections”), so extending `InstructionDefinition` with an optional `sections` field and enforcing it in the existing doctor pass is the lighter, more cohesive choice. A third axis is **tier handling**: tiers can be resolved at compile time (emit three artifacts, one per tier) or at run time (one artifact with conditional sequencing); run-time selection is preferred because it keeps a single source of truth and lets `murmur run --tier extended` pick the sequence dynamically.

## 6. Recommended Approach

The recommendation leads with the compiler and treats execution as an optional convenience. The durable, differentiating value is the **portable orchestration IR** — the ability to author a governed pipeline once and compile it to a Copilot master agent and a goose recipe — and that value is fully realized by v0.2's compile path alone, with no execution at all. On top of that core, `murmur run` is added as an explicitly optional, clearly-secondary driver: a dev-loop convenience for users who happen to have a `claude` or `goose` CLI, never a competitive “execution” surface and never a peer of compilation. This framing matters because the enforced-governance delta that `run` adds over a pure compiler is genuinely thin (see below), so the plan does not stake murmur's identity on it.

The hybrid splits orchestration into two parts, and honesty about the split is the conceptual key. **What murmur actually enforces deterministically is a narrow set:** iteration-counting against the hard loop caps (so a critic↔planner loop can never exceed its `max`), subprocess concurrency-capping through a local worker pool (so `maxConcurrent` and `neverParallel` are real limits on how many host CLIs run at once), rubric *arithmetic* — the weighted-total, severity-count, and gate comparison computed from numbers the host already produced — and RUN-LOG formatting. **What murmur does not own is everything generative:** which agents a phase dispatches (the `invokeWhen`/`skipWhen` predicates in the reference fixture are natural-language, so the judgment is delegated to the spawned host agent), whether a natural-language early-exit condition such as “all dimensions ≥ 4, combined score non-decreasing” is satisfied (the host evaluates it, because it depends on reading generative scores), and what score each dimension earns (assigned by the host critic, not computed by murmur). Even gating is only “deterministic” in the trivial sense that murmur compares two numbers — the *numbers* are generative inputs. So murmur makes real guarantees about the mechanical caps and the arithmetic, and makes only best-effort, parse-conditional contributions to dispatch selection, early-exit, and gating. The plan states this plainly rather than implying murmur governs the decisions themselves.

The approach is sequenced to de-risk, and the de-risking order also reflects where the value is. The pipeline IR and its two compile targets come first and are provable without any execution at all — a pipeline that compiles to a valid Copilot master agent and a valid goose recipe is independently valuable and testable with golden files, exactly as the v0.1.0 adapters were, and it is the milestone the plan is willing to ship and stop at if adoption signal is weak. Only once the IR and compilation are solid does the optional `run` get built, and `run` itself is built in two stages: first the deterministic skeleton (sequence phases, count iterations, write the RUN-LOG, with agent turns stubbed by an echo command in tests), then the host-CLI delegation gated behind an explicit `--allow-run` opt-in. This means every layer is testable offline: the IR with golden files, the driver's bookkeeping with a stub spawn target, and only the final delegation requires a real `claude`/`goose` CLI. The worker-budget concurrency engine (v0.5) slots into the driver's parallel-dispatch step as a direct port of the audio2text `min(configured, rpm, tpm, n_tasks)` algorithm. Rubrics and output contracts (v0.3) are pure additions that strengthen `doctor` and add `score`. The later milestones (v0.4 dispatch tables and classifier, v0.6 adapters and plugins, v0.7 DX hardening) are deliberately **gated on adoption signal** rather than committed up front — the plan proves the governance thesis in-market through v0.2–v0.3 before funding the rest. Throughout, the guiding rule from v0.1.0 holds: the deterministic CLI never summons an LLM; if a step needs generation, murmur spawns a host CLI that the user already trusts and authenticates.

## 7. Architecture & Design

**The pipeline IR.** A pipeline lives at `murmur/pipelines/<name>.md` as a small frontmatter block (name, description, version, classification-set) over a strict-subset YAML body holding the structured orchestration. The single most important correction over the first draft is that the IR is **not a single linear `phases[]` list** — it cannot be, because the reference fixture has two distinct branches selected by a classification gate. The structured shape, drawn directly from `architect.agent.md`, is therefore: a top-level `routing` block declaring the classification step (the phase at which routing occurs, e.g. `0b`, and the set of classifications it can yield — `CODING`, `RESEARCH`, `HYBRID`); a `branches` map where each named branch (`coding`, `research`) carries its own ordered `phases` list; and within each phase an `agents` list whose entries carry a `name`, an optional `builtin` flag, and a `dispatch` object with `invokeWhen`/`skipWhen` string-predicate arrays. The CODING branch thus holds Phase 0→0b→1→2→3→4→5→5b(→5c) and the RESEARCH branch holds Phase 0→R1→R2→R3→R4→R5→R5b, and `routing` names which classification selects which branch. Alongside each branch sit a `loops` list (each with `name`, `from` phase, `to` phase, `min`, `max`, and an `earlyExit` condition string, with `max` hard-capped at three to mirror the architect's safety rule), a `parallel` object (`maxConcurrent` plus a `neverParallel` list of agent pairs), and a `tiers` list — and tiers are now correctly modeled as named **subsets of phase ids *within a branch***, not subsets of one global phase list, each with optional per-loop iteration overrides. Validation (`validatePipeline`) checks that every referenced agent resolves (against the agent and subagent sets plus a known built-in roster), that each branch's loop `from`/`to` reference real phases *in that branch*, that `max` does not exceed the cap, that `routing` classifications each map to a declared branch, and that every tier names only phases declared in its branch; `doctor` folds these into its existing reference-integrity and cycle checks. Because the frontmatter parser cannot read arrays-of-maps, this body YAML is parsed by a strict, minimal, formally-specified reader (detailed below) that **hard-errors on any construct outside the documented subset** rather than guessing — still hand-written, still zero-dependency.

**The strict pipeline-body YAML subset.** The body reader is deliberately *not* a general YAML parser; treating it as one would reimplement the fragile thing zero-dependency was avoiding. It accepts a closed, documented grammar: two-space-indented block mappings, block sequences of scalars, and block sequences of mappings (the one shape the frontmatter parser lacks), with scalar values limited to strings, integers, and booleans. Anything else — tabs, flow/inline maps, anchors, multi-document markers, tag directives, inconsistent indentation, or a value type the schema does not expect — produces a precise `PARSE-ERROR` naming the file, line, and offending construct, and aborts the load. There is no silent-mis-parse path. The alternative of vendoring one tiny vetted YAML dependency for pipeline bodies only was weighed explicitly: it would reduce hand-rolled-parser correctness risk, but it breaks the standing zero-dependency invariant that every downstream consumer relies on and that distinguishes murmur operationally. The decision is to keep zero dependencies and pay for it with a *narrow, strictly-erroring* grammar plus a dedicated negative/fuzz test corpus (section 9), accepting the maintenance cost as the price of the invariant. This makes the body reader a named single-point-of-failure that is mitigated by strict erroring and property testing rather than by trust.

**Compilation and degradation.** The `RuntimeCompiler` interface gains an optional `compilePipeline(pipeline, ctx)` method; `emitAll` calls it only when present, so existing adapters keep compiling without change. The Copilot adapter emits a master `architect`-style `.agent.md`: the branches, phases, dispatch tables, loop limits, and parallelism caps render as structured prose tables in the body, and the union of referenced agents becomes the frontmatter `agents` roster so `runSubagent` can reach them. The goose adapter emits a recipe whose `sub_recipes` encode the phase agents — but here the plan must be honest about a real limitation the analyst verified: the current goose adapter emits `sub_recipes` as a **flat, unordered list of `{name, path}` entries with no sequencing, loop, or parallel-cap keys**, and the goose recipe schema as emitted has no native way to express loop iteration bounds or never-parallel exclusion. So the goose pipeline compilation encodes ordering only as advisory metadata (an explicit `sequence` list and `loops`/`parallel` blocks emitted as recipe metadata the engine may or may not honor), and the structural caps it cannot express natively are recorded as declared degradations in the emitted recipe and in the compile report. Concretely this means **goose pipeline output is advisory-only with respect to loops and parallel caps, the same status as Copilot's prose**; only `murmur run`'s own worker pool enforces those caps. The per-runtime degradation rule is therefore explicit and declared across all three levels: Copilot (roster + persona) gets full prose-table fidelity but every cap is advisory and, lacking a headless CLI, can never be executed by `run`; goose gets structural sub-recipe sequencing but loop/parallel caps degrade to advisory recipe metadata; and a runtime with neither (a future Cursor) collapses the pipeline to a single composite agent or a no-op with a recorded warning. Numeric caps are *enforced* (not merely advisory) only when the pipeline is executed under `murmur run`'s own worker pool against a `claude` or `goose` subprocess.

**Rubrics and output contracts.** A `rubric` is a first-class IR kind at `murmur/rubrics/<name>.md`: frontmatter name and description over a strict-subset YAML body of `dimensions`, each with a label, a `MANDATORY`/`CONDITIONAL` classification, a mandatory/optional question list, a one-to-five scale, and a weight, plus top-level `severityLevels` and a `readinessGate` (e.g. all mandatory dimensions ≥ 4). Two extensions are required so the IR can actually reproduce the reference review format (criterion 10), neither of which the first draft modeled. First, **conditional dimension selection**: a flat `dimensions[]` with mandatory/optional flags cannot express that an internal-refactor task scores only dimensions 3, 5, 6, 7, 9, 11 while a security-critical task makes all dimensions mandatory. The rubric IR therefore carries each dimension's `MANDATORY`/`CONDITIONAL` status plus an optional `appliesWhen` predicate and an `naWhen` predicate, and the score computation excludes `N/A` dimensions from the denominator so a partial scorecard still totals correctly. Second, **weighted multi-rubric aggregation**: the reference combines a technical scorecard out of fifty-five with a business scorecard out of forty and a social scorecard out of forty into a single weighted multi-critic total (the RUN-LOG shows totals like `105/130` and `106/135`, with the denominator varying as social is included or marked N/A). The model adds a `rubricSet` construct — a named set of rubrics each with a weight and an `includeWhen` predicate — and `murmur score` computes per-rubric subtotals and the combined weighted total over only the included rubrics, so the denominator floats correctly when a rubric is N/A. `doctor` validates rubric and rubric-set structure; `murmur score <document> --rubric <name>` (or `--rubric-set <name>`) parses a target document's per-dimension scores and computes the weighted total, severity counts, and pass/fail against the gate — pure arithmetic over numbers the host critic already wrote, no LLM. This presupposes a **machine-parseable score-emission contract**: the critic agent must emit each dimension's score in a fixed, documented line format (a labelled `| <dimension> | <n>/5 |` table row and a `Total: <n>/<d>` line), and the `score` parser is specified against exactly that contract, erroring rather than guessing when a document does not conform. Output-section contracts extend `InstructionDefinition` with an optional ordered `sections` array; when present, `doctor` (and a host agent reading the compiled instruction) can assert that a governed document contains those sections in order.

**The run driver.** `murmur run <pipeline> [--tier <t>] [--allow-run] [--dry-run]` loads and validates the pipeline, classifies the task to select a branch (delegating the classification judgment to the host, since it is generative), resolves the tier to a phase subset *within that branch*, and walks the phases. For each phase it determines the dispatch set — and here the honest split applies: where an `invokeWhen`/`skipWhen` predicate is a simple flag it is evaluated deterministically, but for the reference fixture the predicates are natural-language, so the judgment is delegated to the spawned host agent rather than interpreted by murmur. It caps concurrent subprocesses through the v0.5 worker pool, and for each agent turn spawns the configured host CLI — realistically `claude` or `goose`, never Copilot, which has no headless CLI — via `Bun.spawn` **with an argv array, never a shell string**, capturing output to the `_architect/` tree (the output directory is configurable, defaulting to `_architect/`). It counts loop iterations against the hard caps (the one guarantee it fully owns), and for natural-language early-exit conditions it asks the host to evaluate them rather than evaluating prose itself. It computes rubric scores only where the host emitted machine-readable numbers per the score-emission contract, and writes a `RUN-LOG.md` row (date, slug, tier, iterations, total score, verifier verdict, notes) in the agri format. Crucially, the subprocess path is **gated behind an explicit `--allow-run` opt-in** (mirroring the existing `--allow-config-exec` precedent in `loadConfig.ts`), and the driver validates that every dispatched target resolves only to a declared in-repo agent before spawning. `--dry-run` performs all bookkeeping with a stub echo command instead of a real host CLI, so the entire control flow is testable offline. Where no host CLI is configured or available — which is *always* the case for Copilot users — `run` degrades to compile-and-instruct: it compiles the orchestrator and prints the exact manual steps, never executing.

**The concurrency engine (v0.5).** A hand-written worker pool computes `effective_workers = min(configured, rpm_budget, tpm_budget, n_tasks)`, dispatches up to that many spawns concurrently, and retries transient failures with exponential backoff — a direct port of the audio2text algorithm, enforcing the `neverParallel` pairs and `maxConcurrent` cap as hard limits during execution.

**Dispatch tables, classifier, and rosters (v0.4).** Agent frontmatter gains optional `invokeWhen`/`skipWhen` arrays (read by the existing parser as block scalars), making selective dispatch machine-readable; `murmur classify <task>` matches a task description against a task-category table to recommend an agent set; and the base library ships generic business-critic, social-critic, data-critic, fact-checker, and verifier templates. **DX hardening (v0.7)** adds an `init`-time `lefthook.yml` and CODEOWNERS generator, a `defineCollection`-style typed validation surface exported for plugin authors, and `murmur docs`, a markdown-to-HTML compiler (modeled on the chat `build.py` pattern) that renders an agent pack plus its run-logs into a browsable guide.

## 9. Test Plan

Testing follows the v0.1.0 discipline: golden files for compilation, deterministic fixtures for logic, and offline-by-default — but with one deliberate correction over the first draft, the *risky* paths (host-output parsing, body-YAML parsing) are pulled into CI rather than left to manual exercise. For the pipeline IR, a validator test feeds the reference `architect.md` pipeline and asserts that **both** the CODING and RESEARCH branches plus the classification routing and per-branch tier subsets load cleanly, then feeds malformed variants (an agent reference that resolves to nothing, a loop `max` of four, a `neverParallel` pair naming a missing agent, a loop `from` pointing at an unknown phase, a routing classification mapping to no branch, a tier naming a phase outside its branch) and asserts each produces a precise, file-and-field-scoped error. The strict body-YAML reader gets a dedicated **negative-parse and fuzz corpus**: tabs, flow/inline maps, anchors, multi-document markers, inconsistent indentation, and arrays-of-maps that the frontmatter parser cannot handle must each yield a precise `PARSE-ERROR` naming file and line — never a silent mis-parse — and a property/fuzz test asserts the reader either parses to the expected shape or errors, never returns a wrong shape. Compilation is covered by golden-file tests: the reference pipeline compiles to a Copilot master `.agent.md` whose frontmatter `agents` roster equals the union of referenced agents across both branches and whose body contains the phase, loop, and parallelism tables, and to a goose recipe whose `sub_recipes` match the phase agents; a **goose-recipe-consumption check** asserts the emitted recipe is loadable by goose (or, per the spike outcome, that the advisory-only degradation is recorded); the atomicity guarantee is re-asserted by failing the pipeline adapter mid-emit and checking the output tree is untouched.

The `run` driver is tested entirely offline using the `--dry-run` stub spawn target. Tests assert that phases execute in branch-and-tier-resolved order, that a critic↔planner loop stops at its `max` cap, that an early-exit condition's bookkeeping terminates the loop before the cap, that v0.2c records intended concurrency and (from v0.5) `neverParallel` pairs never co-dispatch and `maxConcurrent` is respected, and that the emitted `RUN-LOG.md` row matches the agri column format exactly (date, slug, tier, iterations, total, verdict, notes). A separate test confirms the compile-and-instruct degradation path prints the manual steps when no host CLI is configured (the permanent Copilot path) and writes nothing it should not. Critically, the **host-output-parsing path is CI-gated, not manual**: a test spawns a *stub host CLI* emitting realistic-but-fixed structured output and asserts the score parser extracts per-dimension numbers and the gate fires; companion tests feed **malformed, oversized, and injection-bearing host output** and assert each is handled as a soft failure — the run records an "unscored" RUN-LOG row and continues, output is size-limited and never `eval`'d or interpolated into a shell, and no crash occurs. The worker pool is unit-tested against the audio2text corner cases — `effective_workers` is the minimum of the four bounds, retries back off exponentially, and a permanently-failing task surfaces a soft failure that still logs. Rubric scoring is tested as pure arithmetic over host-emitted numbers: a fixture document with known per-dimension scores in the documented score-emission format yields the expected weighted total, severity counts, and pass/fail against the readiness gate; a **multi-rubric `rubricSet` test** asserts the combined weighted total (technical /55 + business /40 + social /40) computes correctly and that the denominator floats when social is marked N/A; a **conditional-dimension test** asserts an internal-refactor scorecard excludes N/A dimensions from the denominator; and a document missing a contracted output section fails `doctor`. The classifier is tested by feeding representative task descriptions and asserting the recommended agent set. Finally, the knowledge-externalization gate and the existing twenty-five tests must continue to pass unchanged, and the new base-library rubric and critic-roster templates must themselves pass `doctor` and the externalization scan. In-runtime functional execution against a *live* Claude or goose CLI remains out of scope for automated CI and is exercised manually, but — unlike the first draft — the parsing and soft-failure behavior around that execution is fully CI-covered via the stub host CLI, so the riskiest hypotheses are validated by the suite.

## 10. Risks & Mitigations

The single highest-concern risk — omitted entirely from the first draft — is the **code-execution and prompt-injection surface that `murmur run` introduces**. Spawning a host CLI is a net-new capability with no precedent in v0.1.0, and it carries a real worst-case blast radius: a shared or published pipeline could name an arbitrary host command in `murmur.config`, and if `run` interpolated pipeline-supplied strings into a spawned command, that would be arbitrary command execution on the developer's machine (OWASP A03 injection). The mitigations are layered and must be in the architecture, not merely noted here: the subprocess path is gated behind an explicit `--allow-run` opt-in mirroring the existing `--allow-config-exec` precedent in `loadConfig.ts`; spawning uses `Bun.spawn` with an **argv array, never a shell string**, so no shell interpolation occurs; the driver validates that every dispatched target resolves only to a declared in-repo agent before spawning; and because pipelines can reference executable config, the constrained config loader's threat model extends to pipelines — a pipeline that triggers config execution inherits the same `--allow-config-exec` gate. Closely related is the risk of **treating captured host output as trusted**: a spawned `claude`/`goose` invocation returns free-form text that must never be `eval`'d, never interpolated into a subsequent shell, and must be size-limited to prevent resource exhaustion; malformed or oversized output is handled as a soft failure that records an "unscored" RUN-LOG row and continues. Finally, pipelines, rubrics, and emitted RUN-LOGs (which embed file paths, slugs, scores, and verdicts) must be added to the `murmur publish` scrub file-set and pass the externalization gate, with a test asserting it, since they are publishable artifacts.

The second risk is **overstated governance** — the temptation to claim murmur enforces more than it does. The mitigation is the honesty discipline established in section 6: the plan, the compiled output, and the documentation each state that murmur deterministically owns only iteration-counting against caps, subprocess concurrency-capping, rubric arithmetic over host-supplied numbers, and RUN-LOG formatting, while dispatch selection, natural-language early-exit evaluation, and the underlying scores are generative and delegated to the host. The corollary risk is that for free-form host output the scoring degrades to "unscored," which collapses gating to bare iteration-counting; this is acknowledged as the *expected* case for unstructured output, not an edge case, and is the reason scoring depends on a documented machine-parseable score-emission contract rather than on parsing arbitrary prose. The third risk is the **hand-rolled body-YAML reader as a single point of failure**: a parser bug could silently mis-read orchestration and produce wrong governance without erroring. The mitigation is to constrain the body to a strict, minimal, formally-specified subset that **hard-errors on anything outside it**, backed by the dedicated negative-parse and fuzz corpus in section 9; the explicit trade against vendoring one vetted YAML dependency was weighed in section 7 and resolved in favor of the zero-dependency invariant plus strict erroring.

The fourth risk is **goose not being drivable per-phase**, which would strand the v0.2d execution path: the current goose adapter emits a flat, unordered `sub_recipes` list with no native loop or parallel semantics, leaving an unresolved fork between invoking the whole recipe once (goose orchestrates, murmur enforces nothing) and invoking goose per-agent-turn (murmur orchestrates, the recipe is bypassed). The mitigation is the v0.2.0 spike that gates v0.2d: if goose cannot be driven per-phase with parseable output, the execution path is dropped and murmur ships the compiler-only pipeline, which is still independently valuable. The fifth risk is **runtime expressiveness mismatch** — a pipeline relying on loop or parallel enforcement compiles to a runtime that cannot honor it (Copilot's prose, goose's advisory recipe metadata), giving a false sense of governance. The mitigation is the explicit per-runtime degradation rule: adapters declare what they drop, the compiled output records advisory-versus-enforced status, and only `murmur run`'s own worker pool actually enforces caps. The sixth risk is **scope creep across milestones and its maintenance cost**; the mitigation is the strict de-risking order plus the adoption gate — v0.2a–d must land and prove the IR and optional `run` before any later milestone opens, and v0.4–v0.7 are funded only on adoption signal, keeping the hand-rolled YAML parser, worker pool, and adapters from expanding the maintenance surface ahead of demand. The seventh risk is **breaking the frozen v0.1.0 schema or tests**; the mitigation is that every addition is additive (new IR kinds, optional interface methods, optional frontmatter fields) and the existing twenty-five tests plus golden files are a release gate that must stay green. Two lower risks round out the register: the **single-file RUN-LOG append race** under concurrent `run` invocations, mitigated by per-run files plus an index or a file-lock and by making the run-output directory configurable (default `_architect/`) rather than hardcoding one agent's filesystem convention; and **dependency creep**, mitigated by the standing zero-dependency rule satisfied by the hand-written strict reader and the `Bun.spawn` delegation model.

## 11. Open Questions & Decisions

The brief surfaced the central architectural questions; here are the resolutions the plan adopts. **Run engine versus compiler** — resolved by leading with the compiler as the durable, differentiating core and making `run` an optional, clearly-secondary local driver that spawns a host CLI and owns only the mechanical bookkeeping (iteration-counting, subprocess-capping, RUN-LOG formatting, rubric arithmetic over host-supplied numbers), never an embedded LLM. **Pipeline IR runtime-agnosticism** — resolved by a branch-aware IR (routing plus named branches plus in-branch tiers) compiled through an explicit per-runtime degradation rule, with adapters declaring dropped constructs and an advisory-versus-enforced distinction, so the IR stays neutral while honesty about each runtime's limits is preserved. **Rubric and contract placement** — resolved as a first-class `rubric` IR kind with conditional dimensions and a weighted `rubricSet` for multi-rubric aggregation (reused across agents, consumed by `score`) and an instruction *extension* for output-section contracts. **LLM dependency in `run`** — resolved by the delegation model: the deterministic CLI never calls a model; generation happens only inside the host CLI murmur spawns. This is explicitly *not* a reuse of any v0.1.0 mechanism — there is no subprocess spawning in murmur today and the init command inverts this direction (it emits an artifact the host invokes) — so `run` is acknowledged as a net-new surface justified on its own merits, not by a non-existent precedent, and gated behind `--allow-run`.

The remaining tactical questions resolve as follows. **Tier handling** is run-time (`--tier` selects the phase subset within the classified branch from a single source of truth) rather than compile-time triplication. **Dispatch-predicate evaluation** is deterministic only where predicates are simple flags and delegated to the spawned host agent where they are natural-language — which, for the reference fixture, is nearly always — so murmur never interprets prose itself. **Early-exit and gating** are likewise delegated where they depend on generative scores; murmur only counts iterations and compares host-supplied numbers. **Host CLI targets** are `claude` and `goose` only; **Copilot has no headless CLI**, so Copilot users always get compile-and-instruct, never local execution, and the plan does not imply otherwise. **RUN-LOG location** follows the established `_architect/` convention and the agri column format but is configurable. **Worker-budget defaults** come from `murmur.config` with the audio2text-style `min(...)` clamp, defaulting to a single worker when unspecified for safety. **Plugin registration** stays as directly-registered TypeScript adapters through v0.5 and gains npm-package discovery only at the adoption-gated v0.6, matching the v0.1.0 deferral. **Skill assets** remain single-file until v0.6, when directory-structured assets and their per-runtime resolution arrive. **The classifier's task taxonomy** is seeded from the architect's task-category table but kept editable in the base library rather than hard-coded. And **whether to dogfood** — yes: murmur's own `murmur/pipelines/architect.md` is the acceptance fixture, and it must round-trip **both** the CODING and RESEARCH branches plus the classification routing, proving the IR can represent a real, in-use dual-branch orchestration.

## 12. Execution Guidance & Sequencing

Execution must follow the milestone order strictly, because the durable value and the risk both concentrate in v0.2 — but they sit in *different* parts of it. The durable value is the **portable orchestration IR and its two compile targets**, which is independently shippable and fully testable with golden files; the risk is concentrated in the optional `run` driver's subprocess execution, which is the net-new surface. The single most important discipline is therefore to prove the pipeline IR and its compile targets *before* writing a line of the `run` driver: a pipeline that compiles to a valid Copilot master agent and a valid goose recipe validates the abstraction the way the v0.1.0 adapters validated the original schema, and it is the milestone the plan is willing to ship and pause at to gather adoption signal. The goose-drivability spike (v0.2.0) runs before the schema freezes, so the once-vs-per-turn goose fork is resolved before any execution code is committed. Only when v0.2a and v0.2b are green should the optional `run` driver begin, and it must be built deterministic-skeleton-first (v0.2c, counting only) with a stub spawn target so the entire control flow — branch classification, phase sequencing, loop caps, early-exit bookkeeping, RUN-LOG emission — is provable offline before the `--allow-run`-gated host-CLI delegation (v0.2d, `claude`/`goose` only) introduces any external dependency. This ordering means the riskiest, most identity-sensitive piece (subprocess execution) is the last thing added and is added on top of a fully-tested deterministic core.

The immediate first action is to add the strict body-YAML reader and the branch-aware pipeline schema, because everything else depends on the IR existing. Dogfooding is the acceptance mechanism: authoring `murmur/pipelines/architect.md` to round-trip the real architect orchestration — **both** the CODING branch and the RESEARCH branch, plus the classification routing and in-branch tier subsets — is both the primary fixture and the proof that the IR is expressive enough; if a real construct from `architect.agent.md` cannot be represented in either branch, the schema is adjusted before it freezes at the end of v0.2b. Definition of done for v0.2 is the conjunction of three gates: `doctor` validates the dual-branch reference pipeline and rejects malformed ones; the pipeline compiles to golden-file-correct Copilot and goose output with the goose loop/parallel caps recorded as declared degradations; and `murmur run --dry-run` walks the reference pipeline offline, counting loop caps and emitting a correctly-formatted RUN-LOG. Milestones v0.4 through v0.7 are **gated on real adoption signal** rather than committed up front — each is independently shippable and is funded only once v0.2–v0.3 prove that users want governed pipelines, with each still gated by its own tests plus the standing requirement that the original twenty-five tests, the golden files, and the externalization gate remain green. The roadmap and CHANGELOG should be updated as each milestone lands, and the `docs/COMPARISON.md` differentiator should lead with the honest durable claim — murmur is the only local, portable system that compiles *and* validates multi-agent pipelines without embedding a model of its own — and describe `murmur run`'s local execution as an optional, best-effort convenience targeting `claude` and `goose`, never as the headline.
