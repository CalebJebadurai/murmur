## Problem Statement

The user has developed sophisticated multi-agent workflows across multiple projects using VS Code Copilot's agent customization system (`.github/agents/*.agent.md`, `*.instructions.md`, `SKILL.md` files), but these workflows are currently project-specific, non-portable across agent runtimes, and lack automation for knowledge extraction from new codebases. There is no reusable package that can be dropped into any project to instantly scaffold a multi-agent system where generic agents derive all contextual knowledge from skills and instructions, where a master agent can spawn specialized subagents on demand when no existing specialist fits, and where the entire framework compiles to multiple agent runtimes (Copilot, Claude Code, goose, Cursor, ACP). The goal is to build Murmuration, a tool-agnostic, CLI-installable bun package that embodies best practices from ECC.tools, AAIF goose, Hermes, and Claude Code sub-agents, providing an init workflow that auto-generates project-specific knowledge, a master agent that orchestrates and spawns subagents dynamically, and a publish step that strips codebase-specific context before sharing.

## Desired End State

A user can run `bun add -g murmur` (or `bunx murmur`) to install the Murmuration CLI globally or execute it on demand. In any project directory, `murmur init` analyzes the codebase using the host agent runtime (Copilot, Claude Code, goose, etc.) and generates a `murmur/` directory containing: abstract agent definitions (generic agents with role descriptions, allowed tools, skill/instruction references), subagent templates for the master agent to spawn dynamically, skill packages (domain knowledge in `SKILL.md` format), and instruction files (behavior rules with `applyTo` glob patterns). The `murmur compile --target <runtime>` command transforms these abstract definitions into the target runtime's native format—`.github/agents/*.agent.md` for Copilot, sub-agent definitions for Claude Code, recipes and skills for goose, `.cursor/` rules for Cursor, and ACP-compatible formats for protocol-supporting editors. The master agent (one of the generic agents) receives task requests, decomposes them, matches subtasks to existing subagents, and when no specialist fits, writes a new scoped subagent definition dynamically, attaches relevant skills/instructions, invokes it, and optionally persists or discards it afterward. No agent definition contains project-specific facts—all contextual knowledge is loaded from skills and instructions. The `murmur doctor` command validates frontmatter syntax, applyTo patterns, and skill/instruction references. The `murmur publish` command scrubs generated artifacts of repository names, file paths, proprietary domain terms, secrets, and author PII, producing a clean, reusable agent pack ready for sharing. The `murmur add agent|subagent|skill|instruction <name>` commands scaffold new definitions interactively. Global commands operate across projects; project-level commands operate within the initialized project. The repository is published as a public bun package on npm and the user's GitHub, with the private repo at `/Users/cnickson/projects/murmur` stripped of any codebase-specific examples before publication. Documentation and examples demonstrate initialization, customization, and multi-runtime portability.

### Out of Scope

The following are explicitly deferred or excluded: (1) runtime-specific agent implementations—Murmuration provides the framework and compilation, not the agent execution runtime itself; (2) hosted API services or cloud infrastructure—all operations are CLI-local, using the host agent runtime already running on the user's machine; (3) visual IDE extensions or GUI tools—this is a CLI-first tool, though it may generate configuration files that editors consume; (4) agent-to-agent communication protocols beyond the host runtime's native subagent invocation mechanism—no custom inter-agent messaging system; (5) telemetry, analytics, or usage tracking—the tool operates entirely offline and sends no data; (6) backwards compatibility with the user's existing 17+ agent files in other projects—those remain unchanged, but the user may manually migrate them into Murmuration format if desired; (7) automatic migration of existing projects to Murmuration—users must run `murmur init` fresh in each project; (8) runtime performance optimization, caching layers, or incremental compilation—first version prioritizes correctness and portability over speed; (9) supporting runtimes that have no concept of subagents or skills—if a runtime lacks these primitives, the compiler may degrade gracefully (e.g., flattening subagent logic into the master agent) but full feature parity is not guaranteed; (10) legal review of generated content before publish—the user is responsible for verifying that scrubbed artifacts are safe to share.

## Constraints and Assumptions

**Constraints:**  
The CLI must run on bun runtime (version >= 1.0.0 as specified in package.json engines field). All file operations must be safe—`murmur init` must not overwrite existing files without explicit confirmation, and `murmur publish` must not modify the original source directory in-place but produce output to a separate directory or branch. The compiler must produce valid output for each target runtime—generated agent files must conform to the runtime's expected schema (e.g., Copilot's YAML frontmatter with description/tools/agents fields). The codebase-analyzer agent must operate within the memory and token limits of the host runtime—if a codebase is too large to analyze in one pass, it must chunk the work or sample representative files. The master agent's subagent spawning must respect the host runtime's invocation protocol—it cannot spawn agents the runtime does not support. The package size should remain small—bundling the CLI and templates should not exceed 10MB to ensure fast installation. The user has no budget for external API keys or services—all agents run locally using the user's existing Copilot/Claude/goose credentials. The publish command must not require manual intervention—scrubbing rules must be codified in configuration, not executed by hand. The framework must not introduce new dependency on proprietary runtimes—if it compiles to Copilot today and Copilot is discontinued tomorrow, the abstract definitions remain valid and can compile to another runtime. GitHub repository creation is pending valid `gh` CLI authentication—the repo exists locally but the remote push has not yet succeeded; this must be resolved before any GitHub Actions workflows can be tested.

**Assumptions:**  
Assumption 1 (Configuration Language): The user prefers TypeScript for `murmur.config.ts` with JSON fallback for simplicity, per the vision document's "leaning TS with JSON fallback" note. The implementation will accept both `.config.ts` and `.config.json` with TypeScript taking precedence. Assumption 2 (Subagent Persistence): Subagents spawned dynamically by the master agent are ephemeral by default—they are written to a temporary directory and discarded after execution unless the master agent explicitly persists them to `murmur/subagents/` based on reusability criteria (e.g., if the same specialist is needed more than twice in a session). Assumption 3 (Skill Packaging): Skills are single-file `SKILL.md` packages by default, with an optional `<skill-name>/` directory structure if assets (data files, diagrams, example code) are needed. The compiler resolves references to both flat and directory-structured skills. Assumption 4 (Compiler Plugin Architecture): The compiler uses a plugin model where each runtime adapter is a class implementing a `RuntimeCompiler` interface with methods `compileAgent()`, `compileSkill()`, `compileInstruction()`. Adding a new runtime requires implementing this interface and registering the plugin in `murmur.config.ts`. Assumption 5 (Init Overwrite Behavior): When `murmur init` is run in a directory that already has a `murmur/` folder, it prompts the user with options: (a) merge new findings with existing definitions, (b) overwrite, (c) cancel. Default is merge. Assumption 6 (Doctor Command Scope): The `doctor` command validates schema correctness (required fields present, valid YAML frontmatter), reference integrity (skills and instructions referenced by agents exist), and glob pattern syntax (applyTo patterns compile without errors), but does not validate semantic correctness of agent instructions or skill content—that is the user's responsibility. Assumption 7 (Publish Scrubbing Rules): The publish command uses regex-based and token-based scrubbing. Configurable scrubbing rules in `murmur.config.ts` include: `repoName` (string to remove/replace), `pathPrefixes` (array of path prefixes to strip), `domainTerms` (array of proprietary terms to redact), `piiPatterns` (regex patterns for emails, names). Default behavior is conservative—if a string matches a pattern, it is replaced with a generic placeholder (e.g., `<REPO_NAME>`, `<PATH>`, `<DOMAIN_TERM>`). Assumption 8 (Target Runtime Feature Parity): Not all runtimes support all features. If a runtime has no concept of skills (e.g., early Cursor versions), the compiler inlines skill content into agent instruction bodies. If a runtime has no subagent protocol, the master agent logic degrades to a monolithic agent with conditional branching. The compiler emits warnings when features are degraded. Assumption 9 (Best-of-All-Worlds Synthesis): ECC.tools and Hermes are evaluated based on public documentation, demos, and blog posts—if detailed implementation is not accessible, the evaluation is based on observable behavior and stated design principles. The synthesis prioritizes: skill-first knowledge model (goose), isolated-context sub-agents (Claude Code), protocol decoupling (ACP), and master-agent dynamic spawning (net-new contribution). Assumption 10 (Global vs. Project Commands): Global commands (`murmur add agent <name>` without a project context, `murmur list` showing global registry) are deferred to a future version—first release focuses on project-local commands only. Global install is supported (`bun add -g murmur`) but commands operate on the current working directory's `murmur/` folder.

## Open Questions

**Question 1 (Second Target Runtime):** The scope specifies implementing compiler adapters for at least two runtimes initially. Copilot is confirmed as the first target since the user's existing workflows use it heavily. Should the second target be **Claude Code** (which has mature sub-agent support and would validate the isolated-context model) or **goose** (which has a well-defined skills model and recipes system that aligns closely with Murmuration's design philosophy)? Both are valuable—Claude Code proves the subagent spawning concept works across runtimes, goose proves the skill-centric model compiles correctly. The choice affects which features are prioritized in the abstract schema. The user may prefer goose since it is open-source and easier to inspect for implementation details.

**Question 2 (Master Agent Identity):** The vision document describes the master agent as "one of the generic agents" that coordinates others, but does not specify whether it is a **dedicated orchestrator agent** (a special agent defined solely for coordination, not used for any other tasks) or an **enhanced generic agent** (e.g., the `architect` agent from the user's existing setup, which already decomposes tasks and invokes subagents, extended with dynamic spawning capabilities). If it is the architect, does that mean every project initialized with `murmur init` includes an architect agent by default? Or is the master agent role a capability any agent can assume by loading a specific skill? Clarifying this affects the agent schema design and the init generator's output.

**Question 3 (Subagent Spawn Trigger Heuristic):** When the master agent decides no existing subagent fits a subtask, what **heuristic** does it use to generate the new subagent's definition? The vision says "writes a scoped agent definition, attaches the relevant skills/instructions," but does not specify how the master agent determines (a) which skills to attach, (b) which instructions are relevant, (c) what tools to allow, or (d) what the role description should say. Is this hardcoded logic (if the task is about data validation, attach the `data-schema.SKILL.md` and `validation-rules.instructions.md`), learned from examples (the master agent has a skill that teaches it how to write agent definitions), or LLM-generated each time (the master agent invokes the host LLM to draft the definition based on the task description)? **Question 4 (Init Codebase-Analyzer Scope):** The init workflow must analyze the codebase and generate skills and instructions, but the **depth of analysis** is unspecified. Should the codebase-analyzer produce only structural/syntactic knowledge (file layout, build commands, dependency list, test runner configuration) or also semantic knowledge (business domain terms extracted from code comments, API contract patterns, error handling conventions)?
